# 3.0 — comms expansion (feature branch plan)

Started 2026-10-28. Everything here is developed on one long-lived feature branch and merges to `main` with
the release that introduces it (PROJECT.md: new features on their own branch). Bugfix releases keep shipping
from `main` meanwhile. Nothing on this page is built yet; it is the plan and the open questions.

## Scope

Three workstreams, one branch:

| # | Workstream | Contents |
| --- | --- | --- |
| A | Manpacks | Backpack radios; radio speakers (a radio played out loud into the world); grabbing the handset of a radio on someone else's back |
| B | Vehicles | Vehicle-mounted radios; exterior infantry phone; crew / cargo / misc intercom (TFAR-style) |
| C | Electronic warfare | Signal jamming; relays; SATCOM |

## Decisions (Duke, 2026-10-28)

- **Testing is local** (Workbench / own server). No branch builds on the Workshop.
- **Order:** shared foundation + B (vehicles) first; then A (manpacks), then C (EW/SATCOM).
- **Borrowed handset:** the owner can still transmit on a manpack radio while someone else holds its handset.
- **Intercom carries normal (direct) speech**, as TFAR does, with a **No Intercom** option. Wanted in the
  radio (VON) menu as one entry that cycles four options instead of frequencies — see B.
- **Jammers are a Game Master prop:** configurable range and frequency band, on/off switch.
- **SATCOM is a static, placeable item that can be carried in the inventory** (TFAR has one like this).

Second round (Duke, 2026-10-28):

- **Branch renamed** to `feature/3.0-comms`. **Test builds are `3.0.N`.**
- **Intercom: any seat can pick any channel** (a platoon commander or JTAC in the back of a helicopter must
  be able to talk to the pilot).
- **Jammers:** players can switch them off and destroy them. They also jam transmissions *from* inside their
  range — never by stopping you keying up, by filling what you send with noise and interference.
- **SATCOM:** no delay; forces half-duplex while in use (can't receive while transmitting) even on a radio
  that isn't half-duplex. It *duplicates your own radios*: link to it and every radio you carry transmits
  through it with its own settings and transmit key — nothing to configure on the SATCOM. Not locked to one
  player: a **Link Radio** action on the deployed terminal, auto-unlink when you walk away. **Immune to
  jammers.** **Unlimited transmit range, normal receive range**: you only hear a far station if it is also
  on a SATCOM.
- **Relays:** placeable by players and Game Masters; use the vanilla relay prop where possible.
- **Direction finding:** stretch goal, not in this branch — leave it for another feature branch.

Third round (Duke, 2026-10-31):

- **Relays repeat a configurable frequency band** (low/high kHz set on the relay), like the jammer's band.
- **SATCOM needs open sky.** Which factions get it is still open.
- **Release is `3.0.0`** (for now). Nothing is published until Duke says so. Expect 2.0.x bugfixes after
  2.0.5 to keep arriving from `main`.
- **Infantry phone on the BTR-70 and LAV-25 only**, but it must be easy to add to modded vehicles (RHS and
  WCS have candidates). See B → Infantry phone.

Survey behind B: `docs/research/2026-10-28-terrain-autoconnect-vehicle-comms.md` §3 (CVON 3.0.1, TFAR,
ACRE2 vehicle radios and intercoms). Its §1 (terrain model, recommendation A + B) and §2 (TeamSpeak
auto-connect) are outside this branch's scope unless Duke adds them.

## Branch strategy (parallel bugfix releases)

- **Branch:** `feature/3.0-comms` (started as the session branch `claude/gallant-knuth-zna9uk`, renamed
  2026-10-28 at Duke's request).
- **Bugfixes go to `main` first**, on their own short branch as usual, and are released from `main` as
  `2.x.y`. They never start on this branch.
- **After each bugfix release, merge `main` into this branch** (merge commit, no rebase — the branch is
  shared and pushed). Doing it per release keeps conflicts small; `LC_Client.c`, `LC_GameStateWriter.c`,
  `lc_core.c` and `lc_radio.c` are where they will land.
- **`CHANGELOG.md`:** this branch keeps an unreleased 3.0 section at the top; merged `main` entries stay
  below it in version order.
- **Versions on this branch:** test builds `3.0.0-test.N`, `N` counting up per test build, local testing
  only; the release is `3.0.0` (Duke, 2026-10-31). (Was `3.0.N`, which would count past the release number.
  Version strings are display-only, so the suffix is safe: `modVersion` buffer is 32 chars.)
- **Protocol:** the first incompatible bridge change on this branch sets `LC_PROTOCOL_VERSION` and
  `LC_GameStateWriter.PROTOCOL_VERSION` to main's + 1. If `main` bumps protocol in a bugfix, the next merge
  re-bumps this branch to main's + 1 again. Only one number per build matters; the two halves of one build
  must agree.
- **Merging into `main`:** only with the 3.0 release, and only on Duke's say-so.

## Shared foundation (build first)

All three workstreams break the same assumption: today a radio is something in *your* inventory, and a
transmission comes from *your* position. The foundation removes that before any feature lands.

1. **Radio source.** A radio carries where it physically is and how you reach it: held/worn (today),
   backpack (yours or borrowed), vehicle-mounted, or speaker. `radios[]` in `game_state.json` gains a source
   kind and an antenna position; the `RTX` announcement carries the antenna position instead of the
   talker's head. Terrain links (`radioRx` / `links[]`) are keyed by transmitter *radio*, not player, since
   two radios of one player can be in different places (manpack on the ground, vehicle radio).
2. **Radio access control (server).** Who may use a radio that is not in their own inventory — a borrowed
   handset, a vehicle radio from a seat, an infantry phone — is a server-side lease: request RPC, distance /
   seat check, replicated holder(s), auto-release past the cable length or on seat change, death, or
   disconnect. Client-trusted audio stays as it is; only *access* is arbitrated. Access is not exclusive:
   a manpack's owner keeps transmitting while someone holds its handset, and any number of players can be
   linked to one SATCOM.
3. **Received-signal model in one place.** Today (2.0.5) quality is distance against range, with terrain taking shares of the range per hill
   (`links[].hills`). Jamming (at either
   end), relays and SATCOM all change it; put the quality calculation behind one function in the plugin (`lc_radio.c`) with inputs
   documented, so A/B/C extend it rather than patch it three ways.

## A — Manpacks, speakers, handsets

- **Manpacks.** Survey vanilla first: which backpack radios exist (`Radio_ANPRC77`, `R107M` family?), whether
  they already carry `SCR_RadioComponent`, and how a worn backpack's radio reaches `SCR_VONController` entries.
  Likely only per-prefab config (range, beep set, duplex) plus making sure a worn backpack radio is listed.
- **Speakers.** A radio switched to speaker plays what it receives out loud at its own position: audible to
  anyone nearby, with or without a radio, positional and occluded like direct speech. Needs a replicated
  "speaker on" flag per radio; each client lists speaker radios within ~60 m in `game_state.json`
  (`speakers[]`: id, position, frequency, key, volume, muffle), and the plugin treats each as a receiving
  radio rendered in 3D rather than in an ear. Your own voice into a radio near a speaker playing the same net
  (feedback) is TFAR's "speakers near transmitters" problem — decide whether to model or suppress it.
- **Handsets.** Action on another player's (or a dropped) manpack: take the handset → lease (foundation 2),
  the radio appears in your VON menu with a "borrowed" marker, transmits from the radio's position, released
  past ~4 m (cable) or by action. The owner keeps using it too (Duke); both can transmit on it.

## B — Vehicles

- **Vehicle radios.** A radio component on the vehicle prefab (modded/added, no prefab overrides of vanilla
  vehicles where avoidable — check `Wiki/engine/config-and-prefab-layering.md`). Usable from configured
  compartments (driver/commander/gunner by default). Listed in your VON menu while seated; antenna at the
  vehicle; range/power higher than manpacks. Survey: does vanilla put any radio on vehicles already, and
  what did Coalition VON 3.0.1 do (`CVON_VehicleRadioComponent`) — approach only, no code reuse (GROUND-RULES 7).
- **Intercom.** Per vehicle, channels **crew / cargo / misc** (TFAR). Each occupant is on one or more
  channels (defaults by compartment: crew seats → crew, passenger seats → cargo). Direct speech by someone on
  the same channel of the same vehicle is heard clear and close (no occlusion, no distance, light intercom
  filter) on top of whatever the room model already does. Game side: `players[]` gains an intercom mask
  (players in the same vehicle are always within 60 m, so the list already covers them); `self` gains the
  listener's mask. Plugin side: a third path beside direct and radio.
- **Intercom in the radio menu.** Feasible in principle: the VON radial menu is a list of `SCR_VONEntry`
  objects, and scrolling over one calls its `AdjustEntryModif` (that is how radio entries tune; LC already
  hooks `SCR_VONMenu.ActionTuneFrequency`). Plan: an `LC_VONEntryIntercom : SCR_VONEntry` added to the
  controller's entries while you are in a vehicle with an intercom (or holding its infantry phone), removed on
  leaving. Scrolling cycles **No Intercom → Crew → Cargo → Misc**, the label shows the current one, the
  default comes from the seat. It has no transmit key: intercom rides direct speech, so selecting it never
  opens a radio. One channel at a time (TFAR's model). Any seat may pick any channel (Duke). To verify on
  Duke's PC: how vanilla adds/removes entries at runtime (`SCR_VONController` add/remove API) and that the
  radial menu redraws when the list changes.
- **Infantry phone.** An action point on the vehicle exterior (rear of tanks/IFVs). Picking it up is a lease
  (cable ~5 m) that puts you on the intercom's misc channel (or a configurable one). Released on distance,
  action, or death.

### Survey results (2026-10-31) and the design they settle

Sources: `docs/research/2026-10-31-vehicle-prefabs-compartments.md`, `2026-10-31-von-entry-api.md`,
`2026-10-31-cvon-vehicle-radio-approach.md` (vanilla 1.8.0.13; CVON `9517a39`, which has **no licence** —
all rights reserved, approach only).

- **What vanilla has:** M151A2 / UAZ469 / UAZ452 carry a `BaseRadioComponent` with an `IntercomTransceiver`
  that no script uses; M923A1 / Ural carry an empty one; command trucks carry a 2000 m `RelayTransceiver`
  (Conflict MHQ). No APC or helicopter has a radio, and VON lists only gadget radios. `EVONTransmitType` has no
  vehicle or intercom notion. Leave all of these alone.
- **How LC attaches to vehicles:** components can't be added at runtime, so an `LC_VehicleCommsComponent`
  goes into delta overrides of the vanilla base prefabs (`Vehicle_Base` children: wheeled car / truck / APC,
  `TrackedVehicle_Base` — no vanilla children in 1.8 — and `Helicopter_Base`), holding only the new block.
  CVON and RHS do the same to the same files. **Verify early in Workbench** that LC's and another mod's
  overrides of one base both survive.
- **Vehicle radio = an LC radio child entity on the vehicle**, spawned by that component and built from a
  radio item base (`RplComponent`, `BaseRadioComponent`, `SCR_RadioComponent` gadget, `InventoryItemComponent`).
  It is not a second `BaseRadioComponent` on the vehicle, because the vanilla one is found first. While you
  sit in an allowed seat it is added as an ordinary `SCR_VONEntryRadio`, which needs a gadget. LC's existing
  radio code (duplex, beeps, ear, volume, channel names, TX keys) then works unchanged. Tuning and power go
  through a server RPC with the seat check, which is foundation 2's lease for vehicles. Frequency is shared
  by the crew; volume and ear stay per player. The antenna is the vehicle, not the talker (CVON transmits
  from the talker). **Verify in Workbench** whether a proxy can tune a vehicle-owned radio directly.
- **Seats:** `ECompartmentType` is only PILOT / TURRET / CARGO. Commander = `TurretCompartmentSlot` with
  `CompartmentUniqueName "CommanderTurret"`; copilot = `PilotCompartmentSlot`. Defaults: pilot, commander and
  gunner seats get the radio and the crew channel, and cargo seats get the cargo channel. Use the vehicle's
  `EventHandlerManagerComponent` `OnCompartmentEntered/Left` (slot owner may be a child: use
  `slot.GetVehicle()`). Back that with one client **reconciler**: on seat events and controlled-entity
  change it computes which LC entries you should have and adds or removes the difference. This also survives
  death and possession, where vanilla clears its entries. CVON polls 4×/s; LC should not need to.
- **Intercom entry (`LC_VONEntryIntercom : SCR_VONEntry`):** works in the radial (scroll → `AdjustEntryModif`)
  given three patches:
  1. A modded `SCR_VONController.SetEntryActive` that refuses it. Otherwise picking it makes it the active
     entry and the radio key sends direct speech.
  2. A null-checked `SCR_RadioComponent.RadioToggle`, which crashes on any non-radio entry.
  3. A modded `SCR_VONMenu.OnAdjustEntry` that relabels without showing frequencies.

  The radial is rebuilt only when it opens. Adding an entry while it is open needs `AddRadialEntry`;
  removing one closes the menu, as vanilla does. Put the intercom entry **last**. TX keys index radios only,
  so they don't shift.
- **Infantry phone:** action contexts can't be added from script. BTR70 and LAV25 already have a rear
  exterior context `push_rear`, so the phone action goes there through per-model overrides. Only these two
  get one (Duke). **Easy to add to modded vehicles:** the phone is its own `LC_InfantryPhoneComponent`
  (context name, cable length, intercom channel as attributes) plus the action in that context; a modded
  vehicle gets a phone with one delta override of its prefab adding the component and the action to an
  existing exterior context, no script. Document it in developer-reference as the integration path, with
  the BTR-70/LAV-25 overrides as the worked example.

## C — Electronic warfare, relays, SATCOM

- **Jammers.** A Game Master prop (asset browser) with a jammer component. GM editor attributes: on/off,
  radius, frequency band (low/high kHz), maybe strength. Players can switch it off with an action on the
  prop, and destroy it (damage → off for good). Server keeps a replicated registry of active jammers so
  clients don't search the world; each client lists the ones that reach it in `game_state.json`
  (`jammers[]`: position, radius, band, strength). Two effects, both on frequencies inside the band:
  - **Receiving inside the radius:** the plugin adds a jamming term to receive quality — near the jammer the
    net is noise; towards the edge a strong signal still gets through.
  - **Transmitting from inside the radius:** keying up still works. The transmitter's jam level rides in its
    `RTX` announcement, and every receiving plugin adds that noise and interference to the transmission,
    wherever the receiver is.
  - SATCOM-linked radios are exempt from both (below).
- **Relays (repeaters).** A relay receives a frequency and re-sends it from its own position with its own
  range. A receiver gets the better of two paths: direct, or transmitter → relay → receiver (each leg with
  its own distance and terrain; quality = the worse leg's). Placeable by players (carried item, deployed) and
  by Game Masters; built on the vanilla relay prop where possible — survey on Duke's PC which vanilla prop that
  is (Conflict's radio relay / antenna props and their components) and whether it can carry our component
  without overriding the vanilla prefab. Same registry pattern as jammers (`relays[]`). A relay repeats
  one **configurable frequency band** (low/high kHz on the relay; Duke 2026-10-31).
- **SATCOM.** An inventory item; deployed, it becomes a static terminal.
  - **Link Radio** action on the terminal links you (any number of players, no exclusivity). Walking away
    past a set distance unlinks you automatically; so does death, picking the terminal up, or the action again.
  - **Duplicates your radios:** while linked, each radio you carry transmits through the terminal with its own
    frequency, key, transmit key and other settings. Nothing to configure on the SATCOM; TX1 long range and
    TX2 short range both work through it.
  - **Transmit:** unlimited range, no terrain, no delay, from the terminal's position.
  - **Receive:** normal. You hear a far station only if it too is transmitting through a SATCOM; a nearby
    station on an ordinary radio is heard by the normal range/terrain rules.
  - **Half-duplex forced:** while linked, you can't receive while transmitting, even on a radio that isn't
    half-duplex.
  - **Immune to jammers**, both ways — the trade is a static terminal for reach.
  - **Needs open sky** (Duke 2026-10-31). Cost is negligible because the terminal is static: on deploy, the
    server casts about 5 upward traces from the antenna (one straight up, four at ~60° elevation, ~100 m). Then
    it re-checks every ~10 s in case something is built over it, and replicates one bool. Every client reads
    the bool; nothing is traced per frame or per client. To verify: whether tree canopies block a trace,
    since vanilla foliage colliders may cover trunks only.
  - Bridge: `self.satcom` (linked, terminal position), `RTX` gains a satcom flag the receiver uses to skip
    range, terrain and jamming.
- **Direction finding:** stretch goal, not in this branch. Summary for a future branch: a DF set gives a
  bearing to transmitters on a frequency (even encrypted); the plugin already receives every transmitter's
  position and frequency in `RTX`, so it would report bearings with quality-dependent error to the game, plus
  a DF item and a HUD compass strip. Moderate size, no audio work.
- **EMP:** not planned.

## Bridge changes (provisional)

Listed here so each lands once, with one protocol bump per test build at most:

- `self.radios[]`: `src` (held / pack / borrowed / vehicle), `pos` (antenna).
- `self.satcom`: linked + terminal position (+ sky view).
- `RTX`: antenna position replaces player position; radio id so links can be per radio; jam level; satcom flag.
- `links[]` / `radioRx`: keyed by transmitter radio.
- `speakers[]`, `jammers[]`, `relays[]` (new), `self.ic` + `players[].ic` (intercom masks).

## Open questions for Duke

1. ~~Relays~~ — configurable frequency band (2026-10-31).
2. SATCOM: ~~open sky~~ yes (2026-10-31). **Which factions get it?**
3. **Jammer strength:** yes, as Duke guessed, it means how much a jammer jams at its closest point. Jam falls
   from that peak at the jammer to nothing at the radius. A received signal survives where its quality beats
   the jam. At 100% even a perfect signal is lost near the jammer; at 50% a strong, close signal still gets
   through right next to it. Recommendation: a GM attribute 0–100%, default 100%. It is one number in
   `jammers[]` and gives a GM "degraded" vs "denied". The alternative is fixed 100%, with radius the only knob.
